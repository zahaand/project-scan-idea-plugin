# Implementation Plan: Scan — Project Facts Collectors

**Branch**: `002-scan-collectors` | **Date**: 2026-06-13 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/002-scan-collectors/spec.md`

## Summary

Implement the `:scan` Gradle submodule: five section collectors (Stack, CodeStyle, Linters,
Tests, Structure) that read a JVM/Java project's facts via the IntelliJ External System and
Platform APIs, and return a `ScanResult` discriminated aggregate. Collectors are decoupled from
IntelliJ APIs behind narrow read-only port interfaces; production adapters wire the ports to the
platform; in-memory fakes make collectors unit-testable without a running IDE.

Two model changes land in `:model` as part of this sprint:
1. `StructureInfo.packageOrganisation` (inference field) replaced by `packageSegments` (raw data).
2. `ActiveRule.breaksBuild: Boolean` widened to `Boolean?` to represent "not detected".
3. `TestInfo` gains `unknownTestDependencies` for unrecognised test-scope deps.
4. New `SectionResult<T>` + `ScanResult` types added to `:model` as the producer/consumer contract.

## Technical Context

**Language/Version**: Kotlin 2.2.x, JDK 21 (JetBrains Runtime)
**Primary Dependencies**: `:model` (Sprint 1); IntelliJ Platform SDK 2025.3.5 (External System
API, JavaPlugin, MavenIntegration, PSI); Kotlin stdlib (XML parsing via `javax.xml`)
**Storage**: N/A — scan layer is stateless; produces in-memory `ScanResult` only
**Testing**: JUnit 5 for collector unit tests (via port fakes); IntelliJ Platform Test Framework
for adapter integration tests
**Target Platform**: IntelliJ IDEA 2025.3.5; JVM/Java projects, Maven + Gradle
**Project Type**: Gradle submodule within an IntelliJ Platform Plugin
**Performance Goals**: No explicit latency target at MVP; scan must complete within IDE
responsiveness expectations (no blocking of the EDT)
**Constraints**: No text-parsing of build files (FR-020); collector isolation — one failure must
not cascade (FR-021); read exclusively via IntelliJ project model (Constitution II)
**Scale/Scope**: Single- and multi-module JVM/Java projects; Maven and Gradle only

**Structure decision**: Port/adapter split. Collector logic lives in `collector/` and uses only
port interfaces. All IntelliJ API calls are confined to `adapter/`. This makes every collector
unit-testable without a running IntelliJ instance (FR-019) and isolates Maven/Gradle asymmetry
inside the adapters.

## Governance — Known Deviations

| Deviation | Scope | Resolution |
|-----------|-------|------------|
| Adapter integration test coverage | Gradle External System import path | Functional integration tests for adapters using IntelliJ Platform Test Framework are added in Phase 9 (T044–T049) for the Maven path where precise declarative fixture data is available. Full Gradle Tooling API import coverage via IntelliJ Platform fixtures is not feasible in this sprint due to External System import complexity; adapters relying on Gradle import state are covered at the compilation/smoke level only. Tracked as tech debt per constitution §Governance: _"Deviations are tracked explicitly as technical debt."_ |
| `ComparableVersion` classpath | scan module | `org.apache.maven.artifact.versioning.ComparableVersion` is consumed from `bundledPlugin("org.jetbrains.idea.maven")` (verified compile-time, Sprint 2). No explicit `compileOnly` dep added to avoid version conflict with the platform's bundled Maven 3 artefact. |
| `LanguageLevelModuleExtension.getInstance(module)` | `IjBuildSystemAdapter` | Research R-002 suggests calling the static interface method directly. In practice Kotlin 2.2 cannot call Java static interface methods from companion/object context; replaced with `ModuleRootManager.getInstance(module).getModuleExtension(LanguageLevelModuleExtension::class.java)` which is functionally identical. |
| `LibraryData` coordinate properties | `IjDependencyAdapter` | Research R-001 lists `LibraryDependencyData.target.groupId/artifactId/version`; these properties exist on `LibraryData` but have differing Java nullability annotations that cause Kotlin 2.2 type-inference failures in combination with Elvis + `return@label`. Replaced with `LibraryData.externalName` parsing (`groupId:artifactId:version` format), which is the stable public API and avoids the inference issue. |
| `TestFrameworkType.Platform` | `scan/build.gradle.kts` | Initial scaffold (T002) added `testFramework(TestFrameworkType.Platform)` in anticipation of Phase 9 adapter integration tests. This registers `JUnit5TestSessionListener` as a JUnit Platform service, which fails to instantiate in plain Gradle test execution (no IntelliJ process context). Removed for Phases 3–8 (all tests are plain JUnit 5 via port fakes). Will be restored with Phase 9 adapter integration tests when `BasePlatformTestCase` or equivalent is introduced. |
